Authentication Service

Registration, login and user management for web applications, with JWT sessions, Google sign-in, roles and an admin panel. Built solo, from the security design to the React UI.

Role
Solo: design, backend, frontend, tests
Backend

Frontend

Code
GitHub repository

What it does

Sign-up and sign-in

Email verification, password reset with one-hour tokens, Google OAuth2.

Access control

USER and ADMIN roles, plus a whitelist or blacklist mode for who may log in at all.

Protection

Rate limits, lockout after failed logins, BCrypt, CSRF for cookie flows, a default CSP.

Operations

Trace IDs in every log line, optional JSON logs, a separate audit log for admin actions.

How a session stays alive

Short-lived access tokens are the easy part. The long-lived refresh token is where sessions get stolen, so most of the design is about it.

  1. 1

    Nothing long-lived in JavaScript

    The access token lives only in memory. The refresh token sits in an httpOnly cookie that scripts cannot read.

  2. 2

    Single-use refresh tokens

    Every refresh retires the old token. The database keeps only a SHA-256 hash of each token ID, never the token.

  3. 3

    Families for clean revocation

    A login starts a token family. Reuse or logout revokes that family; a password change or a blocked account revokes all of them.

  4. 4

    A cap on sessions

    Each user has a limit on active families. When it is exceeded, the oldest session is revoked.

Other decisions

Rate limits with a retry hint

Bucket4j limits per IP on auth and admin endpoints, and one resend per minute per email. A 429 carries Retry-After, so the UI can show a countdown instead of an error.

Lockout that tells the owner

5 failed logins lock the account for 5 minutes, 10 block it. Both send an email, asynchronously, so the login response is not slowed down.

Sensitive admin actions need more

Switching between whitelist and blacklist mode asks for a one-time code and the password. Every admin action goes to its own audit log.

Logs you can follow

A trace ID ties together all log lines of one request. JSON output is one setting away, and app, errors and admin actions go to separate files.

An extra, not a defense

Masked login

An optional mode hides the real login page behind one of ten decoys, from a fake 404 to a cooking recipe. The real form opens through a secret link. It makes automated scanning a little harder; the controls above do the real work.

How it is tested

Backend · JUnit 5, Mockito, Testcontainers

  • Token provider, login attempts and lockout, password rules
  • Integration tests for the auth, admin, profile and masked-login controllers
  • Repositories against a real PostgreSQL started by Testcontainers
